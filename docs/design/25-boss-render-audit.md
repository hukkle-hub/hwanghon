# 전 보스 렌더 감사 — 여섯 리그 × 전 클립

「전체 보스 랜더링해서 적용하자.」

`tools/3d/pose-sheet.html` 로 **여섯 보스(모르버스 GLB 포함) × 모든 클립**을 찍어
한 장씩 눈으로 봤다. 수치 감사(문서 24)에서는 안 나온 것들이 나왔다.

## 1. 먼저 도구부터 고쳤다

첫 판에서 모르버스 시트가 거의 비어 나왔다. 두 가지가 겹쳤다.

- **GLB 를 칸마다 다시 읽고 있었다** — 39칸이면 39번. 느리고, 다 못 읽은 칸은 빈 채로 찍혔다.
  → 리그를 **한 번만** 만들고, 칸마다 쉬는 자세로 되돌린 뒤 클립을 얹는다.
- **카메라가 고정이라 모르버스가 화면 밖이었다** — 사족보행이라 다른 보스와 덩치가 다르다.
  → 리그마다 **쉬는 자세의 크기로 카메라를 잡는다**. 칸마다 잡으면 자세끼리 크기가
  달라져 비교가 안 되므로, 리그당 한 번만.

배율도 이제 아레나 데이터에서 그대로 읽는다 (`bossScale × scale`) — 모르버스는 1.04,
모근체는 1.00, 나머지는 1.22 로 **게임과 같은 크기**로 찍힌다.

## 2. hit 과 stagger 가 «똑같은 클립» 이었다

절차 리그 다섯 전부 이렇게 되어 있었다.

```js
for(const name of ['hit','stagger']) clip(name, .65, [ …같은 트랙… ]);
```

**자세 붕괴(stagger)는 처형이 열리는 순간이다.** 그게 긁힌 것(hit)과 한 글자도 다르지 않은
10° 움찔로 나오고 있었다. 보스를 읽는 게 이 게임의 축인데, 가장 중요한 «무너졌다» 신호에
그림이 없었던 것이다.

나눴다. `hit` 은 그대로 짧은 움찔, `stagger` 는 1.05초짜리 붕괴:

| | 몸통 좌우 | 앞으로 꺾임 | 골반 | 팔 |
|---|---|---|---|---|
| hit | 0.17 rad | – | – | – |
| **stagger** | **0.48 → −0.28 → 0.13** (잔진동) | **0.32** | **−0.13 m** | **늘어짐 ±0.5** |

팔이 늘어지는 게 핵심이다 — 기계가 «힘이 빠졌다» 는 건 팔로 읽힌다.

> **모르버스는 원래부터 둘이 달랐다.** bpy 리그(`build_marsh_boss_v2.py`)에는 `f_hit`
> (뒤로 움찔)과 `f_stagger`(머리 떨구고 비틀)가 따로 있다. 나중에 만든 절차 리그
> 다섯이 그 구분을 안 가져온 것이다.

## 3. 도구가 나를 속일 뻔했다 — `times=peak`

처음엔 「hit·stagger 가 아예 안 움직인다」로 보였다. 세 칸(t=0 / 0.5 / 1)이 전부
쉬는 자세였다. 그런데 클립을 뜯어 보니

```
hit: times [0, .15, .35, .65]  values [0, .17, -.09, 0]
```

**t=0.5 (=0.325초) 가 하필 영교차점**이었다. 짧은 클립은 0/0.5/1 로 찍으면
「되돌아오는 지점」에 걸려 멀쩡한 클립도 죽은 것처럼 보인다.

`times=peak` 를 넣었다 — 클립마다 **쉬는 자세에서 가장 멀어지는 순간**을 찾아
가운데 칸에 쓴다. 위 표의 대비는 그렇게 찍은 것이다 (hit t=0.23, stagger t=0.17).

## 4. 모르버스가 어둡다는 내 첫 판단은 틀렸다

시트에서 모르버스만 시커멓게 나와서 「재질이 너무 어둡다」고 적었다가, 재 보고 지웠다.
**bpy 의 기본색은 선형인데 JS 리그의 `0x……` 는 sRGB 다.** 그대로 견주면 8배쯤
어두워 보인다. 같은 선형 공간으로 옮겨 비교하면:

| 재질 | 선형 반사율 |
|---|---|
| 모르버스 가죽 | 0.041 |
| 모근체 나무껍질 | 0.050 |
| 파쇄 기갑 강철 | 0.121 |
| 수문기 본체 | 0.123 |
| 모르버스 갑각 | 0.117 |
| 계전기 강철 | 0.169 |
| 소생기 법랑 | 0.647 |

모르버스 가죽이 제일 어둡긴 하나 모근체와 거의 같고, 갑각은 기갑·수문기와 동급이다.
**이상값이 아니다.** 어둡게 보이는 건 어두운 가죽이 몸 대부분을 덮고 밝은 악센트가
적어서인데, 그건 수치 오류가 아니라 디자인 선택이다 — 이미 배포돼 플레이된 보스의
외형을 내 판단으로 바꾸지 않았다. 바꾸려면 디렉터 지시를 받는다.

> 이 세션에서 잘못된 지표로 결론을 낼 뻔한 게 이번이 **세 번째**다
> (최고속=접점, 헤드리스 프레임, 선형 vs sRGB). 재기 전에 **단위부터** 맞추자.

## 6. 디자인 시트가 앱에 아예 안 들어가고 있었다

「전에 프로젝트내에 디자인 시트 뽑은거 있을거야. 다 적용시키자.」

`design-sheets/` 에 원본 설계 시트 **14장**이 있다 — 화면 시트 10장(컨셉·인력사무실·의뢰·
파티·인벤토리·강화·프로필·결과·벤치마크·허수아비)과 캐릭터 시트 4장.

이걸 가리키는 화면이 셋이다.

| 화면 | 쓰임 |
|---|---|
| `compare.html` | 설계 시트 ↔ 구현 화면 겹쳐 비교 |
| `characters.html` | 「캐릭터 시트」 버튼 |
| `board.html` | 컨셉 시트 링크 |

**그런데 `tools/build-www.sh` 의 복사 목록에 `design-sheets` 가 없었다.**

```sh
cp -r index.html *.html css js art vendor maps manifest.json sw.js www/
#                            ↑ design-sheets 가 빠져 있다
```

`www/` 가 Capacitor 의 webDir 이므로 **안드로이드 APK 안에는 시트가 한 장도 없다.**
앱에서 저 셋을 열면 전부 빈 칸이거나 404 다. 온라인이든 아니든 마찬가지다 —
파일 자체가 패키지에 없으니까. (스크립트에는 `find www/art … design-sheets … -delete`
라는 낡은 줄도 남아 있었다. 시트는 `art/` 밑에 있던 적이 없다 — 같이 지웠다.)

고친 것: 복사 목록에 `design-sheets` 추가. `compare.html` 은 9종만 다루고 있어서
빠져 있던 **허수아비 + 캐릭터 4장**을 넣어 **14종 전부**를 볼 수 있게 했다.

> `sw.js` 프리캐시에는 **일부러 안 넣었다.** APK 안에서는 로컬 파일이라 네트워크가
> 필요 없고, 웹에서는 서비스워커가 처음 열 때 받아서 캐시한다. 검수용 2.3MB 를
> 모든 사용자의 첫 로딩에 얹을 이유가 없다.

### 덤 — 빌드에 모캡 원본 28MB 가 딸려 가고 있었다

시트를 넣고 빌드 크기를 재다가 찾았다. `www` 가 **103MB** 였는데 그중

```
www/art/3d/mocap/src   28MB   ← CMU 원본 ASF/AMC
```

`mocap.py` 가 원본을 `art/3d/mocap/src` 에 받아 두고 `.gitignore` 로 막아 둔다.
git 에는 안 들어가지만 **`cp -r art` 는 작업 트리를 그대로 퍼 간다.** 모캡을 한 번이라도
받아 본 기계에서 APK 를 빌드하면 28MB 가 얹힌다.

런타임은 `art/3d/mocap` 을 **한 번도 읽지 않는다** (BVH 는 `mocap_apply.py` 가 GLB 를
구울 때 쓰는 입력이다). 빌드에서 통째로 뺐다.

**103MB → 75MB.** 시트 2.3MB 를 넣고도 28MB 가 줄었다.
