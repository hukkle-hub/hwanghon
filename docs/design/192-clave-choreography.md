# 192 · 클레이브 전투 안무 — 정지 · 예비 · 순간타격 · 무거운 회수 (2026-10-07)

디렉터: «클레이브 세부작업 시작해. 스킬 모션도 넣고 걸음걸이등 세밀하게.»

연결 문서: 18(보스 연계·예고) · 186 §3(주기 창) · 188(사냥의 맛) · 189 §2.3(서버 전투 계약).
이 문서는 **클라이언트가 서버 판정을 더 잘 보여 주는 방법**을 정한다. 피해·피격 범위·반격 성공·보스 위치·기술 시작/종료 시각은 바꾸지 않는다.

## 0. 이번 배치의 한 문장

클레이브는 계속 들썩이는 큰 사람이 아니라, **오래 멈춰 있는 2.5 m 중장갑 보초가 짧은 순간에 셔터와 장검을 폭발시키고 무겁게 회수하는 보스**다.

모든 기술은 아래 네 박자를 공유한다.

```
정지(읽는다) ─▶ 예비(무게를 싣는다) ─▶ 순간타격(서버 hit 시각) ─▶ 무거운 회수(다음 행동까지 빈틈)
```

타격 프레임을 화려하게 만드는 것보다 **타격 직전의 정지와 타격 뒤의 회수**를 길게 두는 것이 우선이다. 붉은 장검·3 m 셔터라는 큰 실루엣이 먼저 읽히고, 불티·고리·화면 흔들림은 그다음이다.

## 1. 절대 깨지 않는 계약

### 1.1 서버가 진실이다

- `server/field-boss-combat.cjs`가 위치·방향·기술·피해·회피·반격·사망을 판정하는 **유일한 권위**다.
- 클라이언트의 시간 재배치는 GLB의 어느 자세를 보여 줄지만 정한다. `duration`, `hits[].at`, `counter[]`, 범위 도형을 늘이거나 당기지 않는다.
- 느린 기기나 탭 복귀로 프레임을 건너뛰어도 서버 시각에서 계산한 `elapsed`로 곧장 올바른 자세에 도착한다. 프레임 수를 세어 판정을 흉내 내지 않는다.
- 서버 hit를 한 프레임에서 건너뛰면 연출만 정확히 한 번 보충한다. 과거 hit를 다시 판정하거나 같은 `seq:hitIndex`를 두 번 재생하지 않는다.
- 서버의 피해·시각·이동 결과는 이번 배치에서 바꾸지 않는다. 기존 셔터 판정에 하드코딩돼 있던 이동 `4.8 m`와 뒤쪽 판정 `0.5 m`만 기술 정의에 이름 붙여, 클라이언트와 시험이 같은 계약을 직접 읽게 한다.

### 1.2 보스 체력은 비공개다

- 체력·최대 체력·비율·남은 타수·색으로 환산한 체력 단계를 서버 메시지에 넣지 않는다.
- 클라이언트도 받은 피해를 누적해 잔여 체력을 추정하지 않는다. 이름표·예고·파티 UI·접근성 UI 어디에도 보스 체력바를 만들지 않는다.
- `bossActs`는 문서 189의 계약대로 위치·방향·동작·시각만 갖는다. 이 문서의 안무 데이터도 자세 매핑뿐이며 생존 수치를 알지 못한다.

### 1.3 화면은 판정을 설명하되 대신하지 않는다

- 붉은 바닥 도형은 서버의 실제 `line`·`cone`·`circle` 범위를 그대로 그린다.
- 셔터 선형 판정은 출발점 뒤 **0.5 m**부터 앞 **7.2 m**까지다. 채움과 외곽선 모두 같은 footprint를 쓰며, 늦게 입장하면 현재 위치·서버 경과·4.8 m 돌진 거리로 출발점을 역산한다.
- 청백색은 서버가 준 반격창을 뜻한다. 청백색이 보였다는 이유로 클라이언트가 반격 성공을 먼저 선언하지 않는다.
- 장검 접점·불티·충격 고리는 서버 hit 시각에 맞추되, 네트워크 지연으로 늦게 받은 경우 현재 시각에 한 번만 보충한다.

## 2. 조사에서 확인한 사실과 황혼의 해석

아래 왼쪽은 제작사가 직접 공개한 내용이고, 오른쪽은 그 사실을 클레이브에 적용한 **우리 설계 해석**이다. 해석을 벤치마크 게임의 규칙처럼 쓰지 않는다.

## 3. 공통 안무 문법

| 단계 | 보이는 것 | 금지 |
|---|---|---|
| 정지 | 발바닥과 셔터 아래가 바닥에 붙고, 머리·장검 방향이 공격축을 먼저 알린다 | 계속 튀는 호흡, 카메라 흔들림, 무의미한 불꽃 |
| 예비 | 골반을 낮추고 몸통을 비틀어 큰 질량을 한쪽에 모은다. 마지막 짧은 구간은 거의 멈춰 접점을 예고한다 | 타격 전에 가장 큰 FX를 써서 접점을 가리기 |
| 순간타격 | 짧은 원본 클립 구간을 압축해 서버 hit 시각에 칼·셔터·바닥 반응을 동시에 맞춘다 | 클라이언트 hit 선행, 서버 범위와 다른 고리 |
| 무거운 회수 | 타격 뒤 무기와 상체가 지나친 뒤, 셔터→골반→발 순서로 중심을 되찾는다 | hit 직후 idle로 팝, 다음 기술 준비를 숨기는 긴 장식 |

- 기술마다 “거의 멈춘 프레임”은 한 번만 크게 쓴다. 3연타인 셔터 폭풍은 각 타의 짧은 recock은 허용하되, 마지막 반격창이 가장 긴 정지다.
- 공격 중 수평 루트 이동은 서버 좌표를 따른다. GLB 루트가 서버를 덧밀지 않는다.
- 선회는 추적 중에만 각속도 제한으로 보간한다. 셔터 돌진이 잠긴 뒤에는 마지막 순간에 목표를 꺾어 따라가지 않는다.
- 발 접점은 실측 위상 `.121`, `.638`을 지난 순간에만 난다. 프레임 건너뜀·루프 랩에서도 접점당 한 번이다.
- 붉은 검 궤적과 손의 광원은 공격축을 보조한다. 플레이어·예고 도형·접점을 가리면 먼저 줄인다.

## 4. 세 기술의 서버 시각과 자세 시각

아래 시간은 모두 서버 기술 시작 `startedAt`을 0 ms로 한 값이다. 굵은 hit·counter 시각은 `server/field-boss-combat.cjs`와 같아야 한다.

### 4.1 셔터 돌진 — 3,400 ms, hit **1,720 ms**

| 서버 경과 | 안무 | 보여야 하는 읽기 |
|---:|---|---|
| 0–650 ms | 정지 · 표적축 확정 | 두 발과 셔터를 붙이고 얼굴·검끝이 공격축을 먼저 본다 |
| 650–1,350 ms | 예비 · 셔터 들기 | 셔터를 들어 질량을 뒤에 싣고 골반을 낮춘다 |
| **1,350 ms** | 돌진 방향 잠금·서버 이동 시작 | 이후 목표가 움직여도 몸과 선형 예고가 꺾이지 않는다 |
| 1,350–1,470 ms | 잠긴 채 버팀 | 앞으로 튀기 전 짧은 압축, 과한 발 구르기 없음 |
| 1,470–**1,720 ms** | 순간 셔터 닫힘·잠긴 전진 | **1,720 ms에 서버 hit와 셔터 접점·불티·고리가 한 번** |
| 1,720–1,850 ms | 관성 추종 | 서버 돌진 이동은 계속되며 상체와 검이 짧게 따라간다 |
| 1,850–3,400 ms | 무거운 회수 | 셔터가 먼저 바닥을 찾고 골반·상체가 늦게 복귀한다 |

원본 `atk_claveshut`의 큰 자세는 유지하되 0–1.9 s의 들기, 실측 **2.033 s**의 충돌, 2.6 s 이후의 회수를 위 서버 구간에 단조 증가로 매핑한다. 매핑은 역행하거나 hit를 지나 점프하지 않는다.

### 4.2 셔터 폭풍 — 4,300 ms, hit **1,315 / 2,135 / 2,955 ms**

| 서버 경과 | 안무 | 보여야 하는 읽기 |
|---:|---|---|
| 0–900 ms | 정지·식재(plant) | 셔터 쪽 발과 골반을 고정해 3연타의 축을 만든다 |
| 900–1,150 ms | 1타 왼쪽 사선 정지 | 첫 부채꼴과 같은 방향으로 몸과 셔터를 기울여 멈춘다 |
| 1,150–**1,315 ms** | 1타 순간타격 | **1,315 ms**, 작은 강도의 첫 접점 |
| 1,315–1,510 ms | 1타 관성 | 곧바로 idle로 돌아가지 않는다 |
| 1,510–1,830 ms | 2타 재장전 | 상체가 반대축으로 천천히 감긴다 |
| 1,830–1,980 ms | 2타 오른쪽 사선 정지 | 1타와 반대 실루엣을 분명히 보여 준다 |
| 1,980–**2,135 ms** | 2타 순간타격 | **2,135 ms**, 중간 강도 접점 |
| 2,135–2,400 ms | 2타 관성 | 마지막 큰 타격으로 무게가 넘어간다 |
| 2,400–**2,600 ms** | 마지막 중앙 들기 | 좌우 사선과 달리 정중앙 실루엣을 만든다 |
| **2,600–2,800 ms** | 반격 정지 | 서버 counter open과 동시에 청백색, 자세는 크게 움직이지 않는다 |
| 2,800–**2,955 ms** | 마지막 순간타격 | 청백색 유지, **2,955 ms에 3타 hit/counter close** |
| 2,955–3,150 ms | 큰 관성 | 세 타 중 가장 큰 접점과 짧은 후행 |
| 3,150–4,300 ms | 무거운 회수 | 셔터와 검을 순서대로 되찾고 발은 미끄러지지 않는다 |

원본 `atk_clavestorm`의 실측 **1.600 / 2.567 / 3.600 s** 접점을 세 서버 hit에 각각 고정한다. 사이 구간만 늘이거나 압축한다. 첫·둘째 hit의 FX는 마지막 hit보다 작아 3연타의 위계를 읽힌다.

### 4.3 용광로 내려찍기 — 3,050 ms, hit **1,540 ms**

| 서버 경과 | 안무 | 보여야 하는 읽기 |
|---:|---|---|
| 0–850 ms | 정지·낮은 압축 | 두 발을 붙이고 골반을 낮춘다. 일반 `atk_slam`의 공중 점프는 억제한다 |
| 850–**1,190 ms** | 셔터 팔·장검 들어 올리기 | 전용 셔터 팔 궤적으로 머리 위 큰 삼각 실루엣을 만든다 |
| **1,190–1,390 ms** | 반격 정지 | 서버 counter open과 함께 청백색, 골반·발·머리 위 손이 멈춘다 |
| 1,390–**1,540 ms** | 순간 하강 | **1,540 ms에 서버 hit/counter close와 바닥 접점** |
| 1,540–1,750 ms | 압축·반동 | 무릎·골반이 충격을 받고 칼은 바닥을 지난다 |
| 1,750–3,050 ms | 무거운 회수 | 손→상체→골반 순서로 일어나고 마지막에 셔터를 세운다 |

내려찍기는 범용 `atk_slam`을 그대로 빠르게 돌리지 않는다. 공중으로 뜨는 원본 하체는 바닥에 앵커하고, `atk_claveshut`에서 표본화한 왼팔·오른팔 궤적으로 들기→정지→내리기를 보강한다. 이 보강도 hit 시각은 바꾸지 않는다.

## 5. 4.8초 중장갑 보초 idle

idle은 4,800 ms 결정적 매크로 루프다. `Date.now()`의 우연한 시작점이나 `Math.random()`으로 자세가 달라지지 않고, 같은 `startedAt + elapsed`이면 30·60·120 fps에서 같은 자세다.

| 루프 위상 | 자세 |
|---:|---|
| 0–1,200 ms | 느린 한 번의 호흡. 골반은 거의 고정하고 원본 idle 한 주기만 늘여 쓴다 |
| 1,200–1,800 ms | 머리가 짧게 전장을 훑고 왼쪽 셔터 팔이 무게를 다시 받는다 |
| 1,800–2,150 ms | 갑옷이 한 번 가라앉고 붉은 코어/검이 낮은 세기로 한 번 숨 쉰다 |
| 2,150–4,200 ms | **긴 보초 정지.** GLB 표본 시각도 고정해 발·골반·셔터 실루엣이 움직이지 않는다 |
| 4,200–4,800 ms | 머리·셔터가 중립으로 돌아오고 원본 clip 끝→시작 이음새에 연결 |

- 원본 idle의 골반 상하 변위는 기준 위치 대비 **35%만** 남기며, 화면 월드 변위는 **7–8 cm 이하**다.
- 발바닥과 셔터 아래는 바닥을 뚫거나 떠서는 안 된다. 호흡 때문에 모델 전체가 승강하지 않는다.
- 머리 회전·셔터 팔 보정은 작은 후처리 각도로 하고, 2.1초 이상의 정지 구간에서는 수치가 실제로 0에 가깝게 수렴한다.
- walk/skill/stagger로 나갈 때 idle 보정은 **90–120 ms**에 사라진다. 한 프레임 팝이나 이전 자세의 누적 회전이 없어야 한다.
- 기술/걷기에서 idle로 들어올 때도 같은 시간으로 섞되, 서버 상태 도착을 지연시키지는 않는다.

## 6. 청백색 counter 의미

청백색(`#64ddff` 계열)은 “강한 냉기 공격”이 아니라 **지금 반격 입력을 서버가 받아 줄 수 있다**는 뜻이다.

- 폭풍: `[2,600, 2,955] ms`, 내려찍기: `[1,190, 1,540] ms`에서만 켠다.
- 범위 면·검 광원·기존 궤적을 같은 청백색으로 바꾸되 새 광원이나 후처리 패스를 만들지 않는다.
- 채움만 바닥에 번지는 대신 같은 geometry 계약의 얇은 외곽선을 함께 둔다. 강남역 B1 암전은 기술 예고 중 0.28, counter·성공 stagger 중 0.12보다 어두워지지 않는다.
- 창이 닫히면 같은 프레임에 공격 고유의 붉은색으로 돌아간다. 성공했을 때만 별도의 청백 반격 burst·stagger가 난다.
- 셔터 돌진에는 counter 창이 없으므로 청백색으로 바뀌지 않는다.
- 색만으로 뜻을 전하지 않는다. counter 창에는 이미 있는 **긴 정지 자세**, 범위 테두리의 안정, 성공 시 stagger라는 형태·시간 단서가 함께 있어야 한다.
- reduced motion에서도 counter 색·정지·범위는 유지한다. 이는 장식이 아니라 전투 정보다.

## 7. 할당·풀·성능 계약

### 7.1 정상 프레임에서 새로 만들지 않는 것

- gait 접점 거리 계산에서 `map`, spread, 임시 배열을 만들지 않고 상수 두 개를 직접 순회한다.
- `updateBossMotion`, idle, 기술 시간 매핑에서 `Vector3`, `Quaternion`, `Color`, 배열, 객체를 매 프레임 만들지 않는다.
- 손 궤적의 표본은 고정 길이 typed array 또는 미리 만든 벡터 슬롯을 순환 사용한다. `clone()`을 매 프레임 호출하지 않는다.
- 다섯 경고 도형(셔터 1, 폭풍 3, 내려찍기 1)의 채움·외곽선은 setup 때 만들고 기술 중에는 geometry 참조만 바꾼다. 매 예고마다 dispose/rebuild하지 않는다.
- 충격·발 접점 고리는 고정 풀에서 꺼내고 수명이 끝나면 숨겨 반환한다. hit마다 geometry/material을 만들지 않는다.
- 불티·먼지·피격점은 현재 typed-array 풀을 유지한다. 최대치를 넘으면 오래된 슬롯을 덮고 풀을 키우지 않는다.
- 새 texture, shadow light, post-process pass는 추가하지 않는다. 기존 한 개의 손 광원과 기존 재질 색을 재사용한다.

### 7.2 수용 기준

| 항목 | 통과 기준 |
|---|---|
| draw call | 동일 장면 기준 상한 **52 calls 이하**. 외곽선·접촉 코어를 풀링한 최종 검수는 데스크톱·모바일 모두 **49 calls** |
| geometry/triangle | 현재 클레이브 모델·LOD를 바꾸지 않는다. 최종 장면 기준선: 데스크톱 약 **557,889 triangles**, 모바일 LOD 약 **194,047 triangles** 이하 |
| steady-state allocation | warm-up 뒤 idle 60초, walk 60초, 세 기술 100회에서 안무·보행·경고·고리 경로의 의도적 `new`/배열 생성 0; heap가 횟수에 비례해 자라지 않는다 |
| frame-rate 독립 | 30·60·120 fps에서 hit/counter 경계를 각 1회 통과하고 같은 `elapsed` 자세가 같으며, 시간 매핑이 단조 증가한다 |
| 휴대폰 | Pixel 7 가로/세로에서 풀·파티클 수가 데스크톱보다 늘지 않고 모바일 LOD가 유지된다 |
| 정리 | 사망·지역 이동·dispose 뒤 경고·고리·궤적·광원·파티클이 남지 않고, 풀 자원은 한 번만 dispose된다 |

성능 수치는 화면의 `renderer.info.render.calls/triangles`와 브라우저 메모리 표본을 함께 남긴다. GC 직후 한 점만 비교해 “할당 0”이라 말하지 않고, 정적 코드 검사와 반복 시나리오의 증가 추세를 같이 본다.

## 8. reduced motion 규칙

`matchMedia('(prefers-reduced-motion: reduce)')`가 참일 때도 게임 플레이 정보는 그대로다.

| 유지 | 줄이거나 대체 |
|---|---|
| 기술 자세와 서버 시각, 바닥 범위, counter 청백색, 실제 접점, 피해 숫자·고정 크기 접점 고리 | 화면 흔들림 제거, idle 부유와 경고 크기 맥동 제거, 공격 중 장식 불티·검 잔상·고리 확대 생략 |
| 셔터 방향 잠금과 3연타 순서 | idle 머리 훑기·몸통 흔들림 50% 이하, 코어 펄스는 색/밝기 변화로 대체 |
| 사망·stagger 같은 상태 변화 | 전체 화면 확대·시차·지속 회전 금지 |

reduced motion이 일반 모드보다 반격하기 쉽거나 어렵게 만들면 실패다. 애니메이션을 통째로 끄고 순간이동시키는 것도 실패다. **의미 있는 자세 변화는 남기고 주변 장식을 줄인다.**

## 9. 검수 장면과 합격선

### 9.1 자동 계약 시험

1. 클라이언트 `CLAVE_MOTIONS`와 서버 `SKILLS`의 `duration`, `hits[].at`, `counter[]`, shape/range가 정확히 같다.
2. 셔터 원본 접점 2.033 s와 폭풍 원본 접점 1.600/2.567/3.600 s가 각각 서버 hit에 매핑된다.
3. 시간 매핑은 0부터 clip 끝까지 단조 증가하고, 정지 구간의 기울기는 snap 구간보다 작다.
4. 30·60·120 fps 및 한 프레임 건너뜀에서 각 `seq:hitIndex` 연출이 정확히 한 번이다.
5. walk 루프 랩을 포함해 `.121`, `.638` 접점이 양발 한 번씩이며 접점 외 프레임에는 고리가 없다.
6. `bossActs`, `field.bosses`, DOM에 `boss.hp`, `maxHp`, `hpPct`나 보스 체력바가 없다.
7. `prepare/evaluate`가 mixer 평가 전에 서버 시각 자세를 정하고, 같은 프레임 mixer를 두 번 평가하지 않는다.
8. 사망·숨김·지역 이동 뒤 모든 효과가 정리되고 재출현 때 이전 `fired`/counter 색이 되살아나지 않는다.

### 9.2 실제 화면 캡처

`tools/2d/clave-motion-scenario.mjs`는 벽시계가 아니라 **렌더 프레임 수**로 기다리고 다음 장면을 남긴다.

- idle: `settle`, `shutter brace`, `long guard`, `loop seam`
- walk: 왼발 접점, 오른발 접점, 접점 사이 공중/전이 프레임
- shutter: 1,400 ms 잠금, 1,600 ms snap, 1,720 ms impact, 2,100 ms 회수
- storm: 1·2타 impact, 2,600 ms counter open, 2,800 ms snap, 2,955 ms final impact, 회수
- slam: 1,190 ms counter open, 1,390 ms hold 끝, 1,540 ms impact, 압축, 회수
- 공통: player hit, counter stagger, 사망 tail, 완전 cleanup

### 9.3 데스크톱

- 1280×720 실제 전투 화면에서 클레이브 전신·발·예고 도형·피해 숫자가 한 장에 읽힌다.
- `hold`와 `impact` 두 장을 겹쳐 보았을 때 셔터/검의 접점 차이가 분명하고, 발은 바닥을 뚫거나 미끄러지지 않는다.
- 예고와 붉은 궤적이 플레이어 캐릭터·이름표를 가리지 않는다.
- 기준 장면에서 52 draw calls 이하를 기록하고, 사망 cleanup은 추가 효과 0개다.

### 9.4 모바일

- Pixel 7 가로 **915×412**와 세로 **412×915**를 모두 찍는다. 모바일 LOD 적용 여부와 draw call/triangles를 같이 기록한다.
- 세로 보스 구역에서는 짧은 변의 월드 폭을 14% 넓히고 카메라 중심을 플레이어↔보스 중간으로 옮겨, 둘의 전신을 한 화면에 둔다. 판정·위치 자체는 움직이지 않는다.
- 터치 스틱·회피·공격·줍기 단추가 예고/알림 때문에 가려지지 않고, 64 px 미만으로 눌리지 않는다.
- 4.8–5.4 m 범위의 가장자리와 counter 색이 작은 화면에서도 구별된다. 전신 샷 외에 손·셔터·발 접점 확대도 본다.
- 기기 화면 밖으로 나간 큰 FX를 근거로 합격시키지 않는다. 접점은 실제 카메라 구도 안에서 확인한다.

### 9.5 reduced motion

- Playwright에서 `reducedMotion:'reduce'`로 같은 장면을 다시 찍는다.
- 서버 hit/counter 시각·예고 크기·색·자세는 일반 모드와 같고, 카메라 흔들림·고리·잔상·2차 파티클만 줄었음을 프레임/카운터로 확인한다.
- 청백색을 보지 못해도 긴 정지→snap→stagger 순서로 반격 가능 순간과 성공 결과를 구별할 수 있어야 한다.

- 공동 피격은 일반 12개, 치명 22개, 사망 30개 파티클을 한 번씩 만들었고 같은 `seq` 재수신은 중복 생성하지 않았다.
- `npm test`는 **715/715** 통과했다. 여기에는 서버/클라이언트 판정 동등성, 30·60·120 fps, 건너뛴 프레임, counter 양 끝 포함, 숨은 체력 계약이 들어 있다.
- 실제 GLB idle의 첫/끝 자세 차이는 최대 약 **0.112°**(`RightLeg`)였다. 4.8초 루프 끝에서 원본 끝→시작으로 이어도 육안 팝이 생기지 않는 범위다.

## 10. 완료 정의와 이번 범위 밖

완료는 “모션 코드가 들어갔다”가 아니라 아래가 모두 참인 때다.

- 서버 계약과 체력 비공개 시험이 통과한다.
- 세 기술이 정지→예비→서버 hit→무거운 회수로 읽힌다.
- 4.8초 idle의 절반 가까이가 실제 정지이며 중장갑 보초처럼 접지한다.
- 청백색은 실제 counter 창에만 나타난다.
- 정상 프레임에서 새 객체를 만들지 않고 기준 draw call/triangle을 넘지 않는다.
- 데스크톱·모바일 가로/세로·reduced motion 이미지를 직접 보고 발·손·셔터 접점을 확인한다.
- 전체 `npm test`가 통과한다.

이번 배치 밖: 보스 피해량·체력·드롭률 조정, 서버 AI 변경, 다른 보스의 고유 AI, 새 모델/텍스처 제작, 장비 외형·강화 빛·칭호, persistent disk. 이 항목들은 안무가 좋아 보인다는 이유로 함께 몰래 바꾸지 않는다.
