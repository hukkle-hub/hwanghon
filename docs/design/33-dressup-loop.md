# 옷 입히는 재미 — 조사와 기획

「이 게임의 다른 재미는 옷을 입히는 재미다. 마영전처럼. 장비 렌더링을 좀
이쁘게 하고 싶게끔 만들어야겠지? 그리고 그 만든 장비를 잘 적용시켜야 옷을
또 사고 싶겠지?」

## 1. 먼저 실제로 띄워 봤다

`viewer.html?equip=1&fit=1` 로 아인·카인을 장비 채로 렌더해서 눈으로 봤다.
**모델 자체는 좋다.** 문제는 딴 데 있었다.

### 1.1 «이쁘게» 쪽 — 무엇이 부족한가

| | 지금 | 왜 문제인가 |
|---|---|---|
| **환경맵(IBL)** | **없다** | `scene.environment` 가 비어 있어 금속이 **반사할 것이 없다**. 강철 건틀릿도 무광 플라스틱으로 보인다. **가장 큰 한 방.** |
| 조명 | 반구 + 따뜻한 키 하나 (+fit 모드에서 둘 더) | 카인은 거의 검게 나온다. 실루엣을 배경에서 떼어 주는 **림 라이트가 없다** |
| 무대 | 갈색 바닥판 + 격자 | 옷을 보여 주는 화면인데 «작업용 뷰어» 로 보인다 |
| 포즈 | 대기 모션 한 장 | 돌려 보거나 자세를 잡을 수 없다 |

### 1.2 붙는 방식의 버그 둘

- **정강이 보호대와 부츠가 같은 뼈(`LeftLeg`/`RightLeg`)에 겹쳐 붙는다.**
  둘 다 끼면 무릎 패드가 이중으로 보인다 (렌더에서 확인).
- **건틀릿이 오른팔에만 있다** (`a_steel_gauntlet` → `RightForeArm` 하나).
  왼팔은 맨팔이라 고장처럼 보인다.

### 1.3 «또 사고 싶게» 쪽 — 근본 원인

| | 지금 |
|---|---|
| **갈아입을 것** | 방어구가 **슬롯당 딱 하나씩, 전부 5개**. 고를 것이 없으니 «옷을 입힌다» 가 성립하지 않는다 |
| **로비의 내 모습** | 메인 로비의 캐릭터는 **배경 이미지에 구워진 그림**이다. 제일 자주 보는 화면에서 **내 장비가 안 보인다** |
| 인벤토리 3D | `iframe` 토글이고 **기본 꺼짐**. 대부분 자기 3D 모습을 한 번도 안 본다 |
| 염색 | 없다. 같은 모델로 다양성을 곱하는 가장 싼 수단인데, **배관은 이미 있다** (`lookOf(id).tint` → `TW_LOOKS` 가 색을 섞는다) |
| 외형 슬롯 | 없다. 마영전은 «성능 장비 / 외형 장비» 를 나눠서, 좋은 성능을 포기하지 않고도 계속 옷을 산다 |

## 2. 기획 — 네 단계

순서는 «한 번 보면 바로 아는 것» 부터다.

### 1단계 — 보는 맛 (이 문서의 구현분)
환경맵 · 조명 · 무대 · 붙는 버그. 던전·뷰어·인벤토리가 **같은 조명 규약**을
쓰게 한다. 새 의존성 없이 `PMREMGenerator.fromScene` 으로 스튜디오를 굽는다.

### 2단계 — 외형 화면 (`looks.html`)
큰 3D 하나, 슬롯별 착·탈, **염색**, 외형 프리셋 3칸, 회전·확대·조명 각도.
로비와 인벤토리에서 바로 들어간다.

### 3단계 — 갈아입을 것
염료 아이템 + 부위별 색. 방어구 **세트 2~3벌** 추가 (`tools/3d/` 의 bpy
파이프라인으로 만든다). 세트 효과가 아니라 **세트 «모양»** 이 목적이다.

### 4단계 — 늘 보이게
로비 배경의 구운 캐릭터를 **내 캐릭터 3D** 로 교체. 파티 카드·프로필의
초상을 장착 반영 스냅샷으로.

## 3. 1단계 구현

### 3.1 `js/studio-env.js` — 반사할 것을 만들어 준다

외부 HDRI 없이, 발광면 몇 개로 방을 만들어 PMREM 으로 굽는다
(three 의 `RoomEnvironment` 와 같은 수법이지만 우리 색으로).

```js
TW_ENV.make(THREE, renderer, 'studio')   // 차가운 천창 + 따뜻한 키 + 붉은 킥
TW_ENV.make(THREE, renderer, 'dungeon')  // 어둡게, 붉은 쪽으로
scene.environment = tex; scene.environmentIntensity = 0.35;   // 던전
```

던전은 **0.35** 로 약하게 넣는다 — 1.0 으로 넣으면 «황혼» 의 어두운 분위기가
날아간다. 옷을 보는 화면에서만 1.0 이다.

### 3.2 `js/look-stage.js` — 옷을 보여 주는 조명 한 벌

키(따뜻함, 위 앞 오른쪽) · 필(차가움, 아래 앞 왼쪽) · **림(붉음, 뒤)** 세 개와
바닥 접지 그림자. 세 화면이 같은 함수를 쓴다 — 인벤토리에서 본 색과 던전에서
본 색이 달라지면 «내 장비» 라는 느낌이 깨진다.

### 3.3 붙는 버그

- 부츠는 `LeftLeg`/`RightLeg`(정강이) 대신 **`LeftFoot`/`RightFoot`** 에 붙인다.
  정강이 보호대와 자리를 나눠 갖는다.
- 건틀릿은 **양팔**에 붙인다 (왼팔은 모델을 X 로 뒤집어 쓴다).

## 4. 확대해서 다시 봤다 — 옷 이전에 몸이 고장나 있었다

전체 샷만 보고 「모델은 좋다」고 넘어갔는데, 디렉터가 확대해서 세 가지를 짚었다.
**얼굴 일그러짐 · 오른팔 없음 · 왼팔에 무기가 뜸.** 다 사실이었다.

### 4.1 오른팔·무기 — 하나의 버그였다

뼈의 월드 x 를 찍어 봤다 (+x = 캐릭터의 왼쪽).

| 포즈 | 오른 팔뚝 | 오른손 | |
|---|---|---|---|
| 바인드 | −0.259 | **−0.300** | 정상 |
| walk | −0.242 | **−0.300** | 정상 |
| **idle** | +0.036 | **+0.209** | **몸을 가로질러 넘어감** |
| **run** | +0.094 | **+0.286** | 같은 증상 |

오른팔이 «없는» 게 아니라 **왼팔 자리로 겹쳐 가 있었다.** 무기는 `RightHandSlot`
에 붙으니 슬롯을 따라가 **왼손 옆에서 떠 보였다.** 두 증상이 한 원인이다.

메뉴·로비가 늘 `idle` 이라 항상 그렇게 보였다.

**원인**은 굽는 쪽이다. `tools/3d/retarget_ain.py` 의 `char_frame()` 이 Hips 회전에서
«오른쪽» 축을 뽑는데, 소스 클립(`Unarmed_Idle`·`Running_A`)에서 그 축이 뒤집힌다.
그래서 같은 `rh=(0.30,…)` 목표가 반대쪽에 찍히고, 팔이 **닿지 않는 곳**으로 뻗는다
(어깨에서 0.686 m, 팔 길이는 0.593 m).

**아인·카인만** 걸린다 — 양손 무기 «carry» 자세를 쓰는 둘이다. 류·세라는 멀쩡하다.

GPT 의 `js/ain-bind-repair.js` 는 이걸 **못 잡는다** (idle +0.209 → +0.078, 여전히
반대쪽). 던전도 같은 증상이었다.

### 4.2 얼굴 — 피부가 «순수 금속» 으로 구워져 있었다

```
Ain_Mesh   roughness 1   metalness 1
```

캐릭터 GLB 가 `pbrMetallicRoughness` 를 안 쓰고 나와서 **glTF 규격 기본값**
(metallic 1 / roughness 1)으로 로드된다. PBR 에서 metalness 1 은 «확산광이 0 인
순수 금속» 이다 — 피부도 천도 머리카락도 전부 뿌연 쇳덩이가 된다. 눈·코·입이
회색 마스크로 뭉개져 보인 진짜 이유다. 조명 문제가 아니었다.

### 4.3 고친 방법 — 이 컨테이너에 Blender 가 없다

굽는 쪽을 고치는 게 맞지만 여기서는 GLB 를 다시 구울 수 없다. **로드 시점 보정막**
둘을 넣었다. 둘 다 **스스로 검사해서 깨진 것만** 고치고, 파이프라인이 고쳐지면
«고칠 것이 없다» 고 보고한다 — 지워도 되는 시점을 스스로 알려 준다.

- `js/pose-fix.js` — 클립을 실제로 평가해 손이 바인드와 **좌우가 뒤집혔는지** 재고,
  뒤집힌 클립의 오른팔 트랙만 정상인 `walk` 에서 가져와 갈아 끼운다.
  대기는 붙잡은 상수, `run` 은 주기를 늘려 흔들림을 남긴다.
- `js/mat-fix.js` — `metalness===1 && roughness===1` 인 재질만 골라 피부 값으로
  되돌린다 (일부러 금속으로 만든 장비는 안 건드린다). 데시메이션이 쪼개 놓은
  정점의 법선도 위치별로 평균 내 턱선의 검은 금을 메운다.

```
아인 idle  +0.209 → −0.288     카인 idle  +0.242 → −0.279
아인 run   +0.286 → −0.299     카인 run   +0.257 → −0.251
류·세라                          손대지 않음 (원래 정상)
```

**함정 하나**: 클립을 갈아 끼워도 **이미 만들어진 `AnimationAction` 은 옛 트랙을
붙들고 있다.** 보정은 반드시 `AnimationMixer` 보다 먼저 돌아야 한다. 테스트가
이걸 잡아냈고, 그 순서를 테스트로 못박았다.

`tests/dressup-assets.test.mjs` 4개 (**169/169**) — 실제 GLB 를 읽어 좌우를 재고,
류·세라를 건드리지 않는지, 두 번 돌려도 같은지, GPT 의 바인드 교정과 겹쳐도
오른팔이 오른쪽에 남는지까지 본다.

### 4.4 아직 남은 것 — 이건 다시 구워야 한다

얼굴이 읽히게는 됐지만 **선명하지는 않다.** 런타임으로 못 고치는 두 가지다.

- **텍스처 해상도**: 2048 맵 한 장이 전신을 덮는다 → 얼굴에 약 256px 이 돌아간다.
- **데시메이션**: 머리 쪽 폴리곤이 과하게 깎여 볼·턱에 면이 보인다.

얼굴만 따로 UV 를 떼어 1024~2048 을 주고, 머리 주변 감소율을 낮춰 다시 구워야 한다
(`tools/3d/decimate.py`, `gen_tex.py`). **Blender 가 있는 환경이 필요하다.**

## 5. 바람 — 머리카락이 흩날리고 옷자락이 일렁인다

> 디렉터: *"기타 알피지처럼 머리카락 흩날린다던가 옷감이 바람에 일렁인다던가.
> 하는 것도 넣어줘야돼. **던전마다 특징을 넣어서**"*

옷을 사고 싶게 만드는 것은 옷의 **정지 화면**이 아니라 **움직임**이다.
마영전의 망토, 몬헌의 장식 천, 검사의 머리카락 — 가만히 서 있어도 실루엣이
살아 있다. 우리 캐릭터는 지금까지 **완전히 굳어 있었다.**

### 5.1 왜 물리 시뮬레이션을 쓰지 않았나

정석은 뼈를 더 심고(head hair chain, cloth chain) 스프링을 매다는 것이다.
하지만 우리 GLB 는 **이미 구워진 스킨 메시**다. 뼈를 더 심으려면 네 캐릭터를
다시 굽고, 모든 클립을 다시 리타게팅해야 한다. 그리고 옷은 앞으로 계속 늘어난다
(3단계에서 방어구 세트가 붙는다) — 세트마다 뼈를 심을 수는 없다.

그래서 **정점 셰이더**로 갔다. 비용이 사실상 0 이고(스키닝 뒤에 벡터 하나를
더하는 것뿐), 뼈 구조와 무관하며, 나중에 붙는 장비에도 같은 규약이 그대로 통한다.
안드로이드에서 프레임이 전혀 떨어지지 않는다는 것이 가장 큰 이유였다.

### 5.2 `js/wind.js` — 어디를 흔들지 «스스로» 잰다

핵심은 **굳기 가중치 `aFlex`** 다. 정점마다 0~1 을 주고, 셰이더는 그만큼만 민다.

```glsl
/* #include <skinning_vertex> 뒤 — 스키닝이 끝난 자리에서 민다 */
if(aFlex > 0.002){
  float ph = uWindT*uWindFreq + transformed.y*2.7 + transformed.x*1.9 + transformed.z*1.1;
  float s  = sin(ph)*0.66 + sin(ph*1.87 + 1.3)*0.34;   /* 두 파장을 겹쳐 «반복» 을 지운다 */
  transformed += uWind * (aFlex * (0.55 + 0.45*s));
  transformed.y += uSway * aFlex * sin(ph*0.83 + 2.1); /* 위아래 들림 — 천이 부풀어 오른다 */
}
```

`aFlex` 를 **손으로 칠할 수는 없다**. 네 캐릭터가 전부 다르고, 앞으로 옷이 계속
늘어난다. 그래서 뼈 가중치에서 지배 관절을 뽑아 **관절 종류별 규칙**으로 굽는다.

#### 머리카락 — 두 번 틀리고 세 번째에 맞췄다

**첫 판**: 「`Head` 관절에서 먼 정점 = 머리카락」. `Head` 관절은 **정수리가 아니라
목**에 있어서, 가장 먼 정점이 **두개골 꼭대기**로 잡혔다. 머리통이 흔들렸다.

**둘째 판**: 「머리 축에서 수평으로 멀고, 아래로 늘어진 만큼」. 테스트는 통과했다
(368 정점이 걸렸다). **그런데 화면에서는 아무 일도 일어나지 않았다.** 개수만 세고
**세기를 재지 않았기 때문**이다. 실제로 재 보니 최대 자유도가 **0.095** — 가장
세게 흔들리는 머리칼조차 **3 mm** 움직이고 있었다.

왜 그랬는지는 메시를 직접 찍어 보고 알았다. **늘어진 머리카락이 아예 없다.**

```
아인  Head 정점 5,749   두개골 밑 1.488 → 정수리 1.680   (전부 19cm 안)
카인  Head 정점 2,361   1.652 → 1.860
류    Head 정점 3,464   1.579 → 1.780
세라  Head 정점 1,717   1.524 → 1.720
```

네 캐릭터 모두 **두피에 붙은 짧은 머리**다. 「아래로 늘어진 만큼」으로 고를 것이
애초에 없었다. 실제 게임의 짧은 머리가 하는 일을 그대로 하기로 했다 —
**머리 껍질이 목을 축으로 기운다.**

```
자유도 = (머리 관절에서의 거리 − r40) / (r95 − r40)       … 목은 0, 바깥 머리칼은 1
```

`r40`·`r95` 는 그 캐릭터 머리 정점 거리 분포의 40·95 백분위다. **고정값은 못 쓴다** —
머리 반지름이 아인 0.146, 카인 0.186, 류 0.193, 세라 0.183 으로 제각각이다.

#### 얼굴은 반드시 빼야 한다

껍질을 통째로 기울이면 **이목구비가 같이 밀린다.** 디렉터가 이미 짚은 «얼굴
일그러짐» 이 다시 나온다. 그래서 **앞쪽 원뿔을 막는다**.

- 앞이 어디인지는 **발끝 뼈**가 알려 준다 (`LeftToeBase` − `LeftFoot`, 네 캐릭터 모두 +z)
- 앞뒤 기준점은 관절이 아니라 **머리 정점의 무게중심**이다.
  세라·류는 머리통이 목 관절보다 **6 cm 앞**에 있어, 관절 기준으로 재면
  **뒤통수까지 «앞»** 이 되어 머리 전체가 막혔다 (세라 자유도 596 → 175 정점)
- 정수리 쪽(높이 80% 위)은 막지 않는다 — **앞머리는 날려야 한다**

#### 그런데 이번엔 머리가 찢어졌다

자유도를 제대로 주고 나니 이번엔 강풍에서 **정수리에 틈이 벌어졌다.** 당연했다 —
치맛단은 80 cm 를 늘어뜨리니 10 cm 쯤 날려도 되지만, **머리통은 위아래로 19 cm 뿐**이다.
거기서 10 cm 를 밀면 머리 껍질이 두피에서 통째로 떨어져 나간다.

머리에만 **별도 배율 `HAIR_GAIN = 0.35`** 를 건다. 옷자락은 그대로 둔다.
짧은 머리가 실제로 움직이는 만큼인 **3~4 cm** 가 된다.

| | 머리칼 정점 | 강풍에서 머리칼 끝 | 옷자락 정점 | 옷자락 끝 | 얼굴 최대 |
|---|---|---|---|---|---|
| 아인 | 2,579 | 3.7 cm | 7,550 | 10.0 cm | 0.0 mm |
| 카인 | 757 | 3.7 cm | 11,870 | 10.6 cm | 2.9 mm |
| 류 | 954 | 3.7 cm | 10,065 | 8.8 cm | 3.8 mm |
| 세라 | 476 | 3.7 cm | 13,740 | 10.6 cm | 0.0 mm |

「얼굴 최대」는 **가장 헐겁게 잡았을 때**의 값이다. 이목구비(무게중심보다 확실히
앞쪽, 이마 아래)는 네 캐릭터 모두 **정확히 0** 이고, 위 숫자는 턱선·관자놀이
가장자리에서 새는 양이다. 강풍 돌풍 정점에서도 **4 mm 미만** — 화면에서 읽히지 않는다.
그래도 0 이 아니므로 적어 둔다.

#### 옷자락

다리·골반 뼈 선분에서의 **거리** × 골반보다 아래로 내려간 정도(제곱). 허벅지에
붙은 천은 안 움직이고 끝단만 크게 움직인다. 이쪽은 첫 판부터 잘 맞았다.

### 5.3 던전마다 다른 공기

같은 흔들림을 어디서나 쓰면 «셰이더 효과» 로 보인다. 장소의 성격이 드러나야 한다.

| 던전 | 공기 | 세기 | 성격 |
|---|---|---|---|
| 훈련장 | 정체된 공기 | 0.008 | 실내. 거의 멎어 있고 7 초에 한 번 느리게 숨 쉰다 |
| 갈대습지 | 습지의 맞바람 | 0.032 | 정면에서 밀어온다. 3.4 초 주기로 몰아친다 |
| 하수 처리장 | 수면의 찬 기류 | 0.012 | 수면을 타고 낮게 흐른다. 방향이 옆으로 눕는다 |
| 변전소 | 송풍기 맥동 | 0.014 | **주파수 3.1** — 기계 냉각팬. 잘고 빠르게 떤다 |
| 식물원 | 온실의 소용돌이 | 0.018 | `swirl` 0.35 — 방향이 **천천히 돈다**. 유일하게 회전한다 |
| 고가 수송로 | 고가의 강풍 | 0.044 | 가장 세다. 옥외 고가. 2.6 초마다 2.4 배 돌풍 |
| 폐병원 | 멎은 공기 | 0.006 | 가장 잔잔하다. 9 초에 한 번, 대신 4.2 배로 훅 분다 |

돌풍은 `pow(sin(phase·π), 6)` — 평소엔 거의 1 이다가 **짧게 확 부푼다**.
선형 사인으로 하면 «계속 일렁임» 이 되어 불안하다.

바람 벡터는 **월드 좌표로 정의하고 물체 공간으로 되돌려** 넣는다. 그래서
캐릭터가 돌아도 바람은 제 방향을 지킨다 — 돌아서면 머리카락이 앞으로 넘어온다.

### 5.4 붙인 자리

| 화면 | 준비 | 묶기 | 갱신 |
|---|---|---|---|
| 던전 (`js/game3d.js`) | 캐릭터 로드 직후 | `TW_WIND.profile(A.id)` | `ainTick(dt)` |
| 협동 (`js/party-online.js`) | `loadCharacter` (유일 로드 지점) | 아바타 생성 시 `this.A.id` | 아바타 갱신마다 |
| 뷰어 (`viewer.html`) | 로드 직후 | `?wind=<던전>` (`off` 로 끔) | 렌더 루프 |

**보정막보다 뒤, 믹서보다 앞**이라는 순서를 지킨다 (§4.3 의 함정과 같다).
협동은 `SkeletonUtils.clone` 이 지오메트리를 공유하므로 **원본에 한 번만**
`prepare` 하면 모든 아바타가 `aFlex` 를 물려받고, `bind` 만 아바타마다 따로 한다
(그래야 각자 다른 위상으로 흔들린다).

### 5.5 검수

`tests/wind.test.mjs` 6 개 — 눈으로 «흔들리는 것 같다» 로 끝내지 않으려고, 실제
GLB 를 읽어 다음을 **센다**.

- 네 캐릭터 모두 머리칼 끝 자유도 **> 0.85**, 평균 **> 0.25**, 옷자락 끝 **> 0.80**
  — 개수뿐 아니라 **세기**를 못박는다. 둘째 판이 여기서 걸렸을 것이다
- **얼굴 최대 자유도 < 0.02** (검사가 헛돌지 않도록 얼굴 정점을 30개 이상
  찾았는지도 함께 본다). 이 검사가 카인 0.163 · 류 0.179 누출을 실제로 잡아냈다
- 던전 7 곳의 바람이 세기·방향·주기에서 **서로 겹치지 않는다** (고가가 최대, 병동이 최소)
- 캐릭터를 90° 돌려도 **세기는 그대로, 방향만 돌아간다**
- 한 돌풍 주기 안에서 세기가 1.5 배 이상 오르내리고 **돌풍 배율을 넘지 않는다**
- 흔들 것이 없는 물체는 **재질을 복제조차 하지 않는다**

그리고 `tools/wind-sheet.mjs` — 믹서를 멈춰 **자세를 고정**하고 던전별 돌풍
정점에서 찍는다. 화면에서 달라지는 것이 오직 바람뿐이라야 비교가 된다.
