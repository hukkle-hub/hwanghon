# 62 · 「아직도 튕긴다」 — 되살릴 수 있는 사고를 막다른 화면으로 처리하고 있었다

52 번에서 고친 것은 «새 빌드가 받아지면 출격 중에도 리로드하던» 경로였다.
그건 맞게 고쳤는데, 디렉터는 여전히 튕긴다고 한다. **다른 길이 남아 있었다.**

## 앱을 끊는 길은 셋이다

| | 무엇 | 지금 |
|---|---|---|
| 1 | 새 빌드 반영 리로드 | 52 번에서 고침 — 출격 중이면 미룬다 |
| 2 | 검은 화면 감지 → 저사양 재시작 | 전투 중이면 설정만 낮춘다 |
| 3 | **그래픽 장치 연결 끊김** | **바로 막다른 오류 화면** ← 남아 있었다 |

```js
el.canvas.addEventListener('webglcontextlost', function(e){
  e.preventDefault();
  fatal('그래픽 장치 연결이 끊겼습니다', …);   // 버튼: 저사양으로 «다시 시작»
});
```

`preventDefault()` 를 부르는 것은 **「복구해 달라」는 뜻**이다. 브라우저는
그 뒤 `webglcontextrestored` 를 보낸다. 그런데 우리는 그걸 듣지 않고 바로
막다른 화면을 띄웠다. 되살아날 수 있는 사고를 죽은 것으로 처리한 셈이다 —
디렉터 입장에서는 그냥 「튕긴」 것이다.

안드로이드에서 이건 드문 일이 아니다. 앱을 잠깐 내렸다 올리기, 화면 끄기,
다른 앱의 메모리 압박 — 전부 컨텍스트를 날린다.

## 고친 것

- `webglcontextrestored` 를 듣는다. 돌아오면 «잠시만» 화면을 걷고 그대로 잇는다.
  전투 상태는 건드리지 않는다 — 컨텍스트만 끊겼을 뿐 싸움은 그대로다
- 복구 직후에는 **블룸을 끈다.** 끊긴 이유가 대개 메모리인데 블룸은 렌더 타깃을
  세 장 더 쓴다. 되살아나자마자 같은 부하를 다시 거는 건 앞뒤가 안 맞는다
- 8 초 안에 안 돌아오면 그때 `fatal` 로 간다. 이유를 `restartCrumb('gl')` 로
  남겨 다음 부팅 화면에 뜨게 한다
- `DIAG.ctxLost` / `DIAG.ctxRestored` 카운터를 남긴다 — 「몇 번 끊겼고 몇 번
  살아났나」를 진단 화면에서 볼 수 있어야 다음에 또 이럴 때 추측하지 않는다

## 정직하게 — 확인하지 못한 것

**이 컨테이너에는 GPU 가 없고(SwiftShader), 컨텍스트 손실을 실제로 일으켜
볼 수단이 없다.** `WEBGL_lose_context` 확장으로 흉내 낼 수는 있지만 그건
브라우저가 «복구해 주는» 실제 경로와 같지 않다. 코드 경로와 논리는 맞다고
보지만, **S25 에서 실제로 튕김이 줄었는지는 디렉터가 확인해 주셔야 한다.**

그리고 애초에 디렉터가 겪은 튕김이 정말 3 번인지도 확정하지 못했다. 1·2 번은
이미 막혀 있고 3 번만 남아 있었으니 가장 유력하지만, **추정이다.**
다음 빌드에서 진단 화면의 `ctxLost` 숫자를 보면 확실해진다 — 0 이 아니면
이게 맞았던 것이고, 0 인데도 튕기면 네 번째 길이 있는 것이다.
